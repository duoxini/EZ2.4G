# Rapoo VT3S MAX initialization and passive battery subscription

This supplement extends RAPOO_VT3S_MAX_PROTOCOL_EVIDENCE.md and corrects its earlier source coordinates. The official main bundle is 131 lines, not one line. All byte offsets here are UTF-8 byte offsets in rapoo_assets/index-WEaXdsQS.js, whose SHA-256 is c4131b8017b3544b198279440d3fcc0b9afe0bd084e9619c59d0b77e3c88bedf.

## Device store initialization

- Main JS line 131, byte 450,724 calls a0().initDevices() on startup after the encrypted maps have loaded.
- The a0 device store's initDevices implementation is at line 93, beginning byte 365,695. It calls navigator.hid.getDevices(), filters against product metadata and collection usages, wraps matching devices, then runs E(device) on each candidate before adding it to the device list.
- E is at line 93, byte 367,971. It calls getFirmwareVerison(device, 0) and returns success only if that completes. initDevices drops candidates for which this fails. The device wrapper constructor installs the parser callback before the device is opened.
- getFirmwareVerison is at line 93, byte 357,007. It looks up CMD.get_firmware, passes argument byte 0 for this initialization call, validates the returned feature report's first byte as 1, and reads firmware version bytes 1 and 2.
- The VT_nrf54L command table maps get_firmware to decimal 163 (0xA3), at line 93, byte 302,105. VT3S MAX has protocol 1 (VT_nrf54L), mouse type 1, featureReportId 8, and no reportId field in its product record. Thus the generic command path defaults to output report ID 6 and response feature report ID 8.
- executeSendCMD is at line 93, byte 316,345. For a wired/USB connection it forms payload bytes FF A3 00. For a wireless receiver it forms A5 A3 00. The report ID passed separately to WebHID sendReport is 6. The Telink +0x20 adjustment does not apply to VT3S MAX. It then reads feature report 8; the generic path retries when response byte 0 is 2, while getFirmwareVerison's acknowledgement check requires byte 0 to be 1.
- fh.send, fh.setInputReportCallback, and fh.getFeatureReport are at line 93, bytes 301,472, 301,506, and 301,701 respectively. The send wrapper calls WebHID sendReport(reportId, data); the read wrapper calls receiveFeatureReport(reportId). This firmware query is the official app's initialization/connection check. It is not the battery query, and the static bundle does not connect it causally to report 7.

## Report 7 subscription and collection usage

- The VT parser registers input report ID 7 at line 93, byte 311,260. The wrapper saves this callback in its inputReportMap during construction.
- fh.open starts at line 93, byte 300,816. It calls device.open() and subscribes to inputreport events, routing each event to the registered callback when event.reportId matches. It does not send a report itself.
- The product-support check accepts collection usage page 0xFF00 with usage 0x0E or 0x02 at line 93, byte 364,954. The fh constructor scans for usage 0x0E on the same page and stores that collection in targetInterface at line 93, byte 300,719. Static search finds targetInterface only declared and assigned; open does not consult it. Therefore the usage 0x02 path accepted by the product filter is not blocked by fh.open or its report-ID callback routing.
- VT3S MAX battery state starts as null in the device wrapper constructor at line 93, byte 315,493. Parser events on report 7 emit the battery state, but the store's initDevices path does not issue a battery-level command. A battery value is populated only when a battery-bearing input report arrives.
- Report 7 payload offsets, status values, and 12-byte parser minimum are described in the main evidence report. Those offsets index the WebHID DataView payload; WebHID exposes reportId separately as an event property. For the native Windows HID API, Microsoft documents that `HIDP_CAPS.InputReportByteLength` includes the leading report-ID byte ([HIDP_CAPS](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/hidpi/ns-hidpi-_hidp_caps)); Windows `ReadFile` obtains input reports from the HID collection ([Obtaining HID reports](https://learn.microsoft.com/en-us/windows-hardware/drivers/hid/obtaining-hid-reports)). Therefore, for report ID 7 with the parser's 12-byte payload minimum, the corresponding native report buffer is 13 bytes: `[0x07, <12 payload bytes>]`. The leading ID is API framing; it is not payload byte 0 in the WebHID parser offsets.
- get_battery_level:[170] remains an unused command-table entry. No call site or active battery request frame was found. Do not infer that 0xAA, the firmware query, or feature report 8 triggers a battery report.

## Practical conclusion

For a strictly passive battery path, the official driver evidence requires opening the permitted HID device and registering the inputreport callback for report ID 7; it does not show a battery-specific write or query. The full Rapoo web-app initialization additionally sends the known read-only firmware query described above and expects feature report 8. That initialization query may be relevant when reproducing the complete web-driver connection check, but it is not necessary evidence for battery decoding and should not be represented as one. The reported 3-second timeout came from the passive `read_rapoo` attempt; the available evidence does not connect that timeout to Rapoo's WebHID feature-report wait.

## Current-configuration initialization read

- The `a0` device-store setup obtains `getCurrentConfig` from `Pp` (line 93, byte 362,829). Its `T(device)` action sets the current device and then calls `M()`; `M()` invokes the store's current-config list function `s(device)`. In `Pp`, `s` is `getCurrentConfig`, and it reads the current index through helper `n`, then the matching configuration name through helper `a` (line 93, byte 354,191).
- For VT3S MAX, helper `n` passes `ADDRESS.CONFIG_CURRENT` to `nr` with length 4 because the protocol is not Telink. Helper `a` passes the selected `ADDRESS.CONFIG_NAME[index]` to `nr` with length 16. `nr` calls `device.sendCMD(device.CMD.read_eeprom, [length, ...address])` (line 93, byte 299,160); the VT_nrf54L command table maps `read_eeprom` to decimal 164 (0xA4) and `write_eeprom` to 165 (0xA5) (line 93, byte 301,169). The callback checks the response ACK via `w0` (first response byte must be 1).
- This initialization path reads the current configuration index/name using A4. The corresponding `sa` helper uses `write_eeprom` A5, but no `sa` invocation occurs in the `T -> M -> getCurrentConfig` path. These reads explain additional initialization traffic, but the code does not show them requesting or triggering the battery report.
